# Audit and protocol for a 250-task analog sizing benchmark

Audit date: 2026-09-10. Scope: repository code and artifacts available before the new benchmark build. This report recommends an admission protocol; it does not claim that the new 250 tasks have already passed it. No training-approval records were changed.

## Findings from the six-task pilot

I inspected the task JSON, the index, the locally stored reference JSON, and all six saved episode summaries. Every indexed task hash matches its task file. All six saved episodes pass on the second evaluation: first the failing initial design, then the supplied reference. This is a reference-replay check, not evidence that an optimizer can discover the answer.

| Property | Observed |
|---|---:|
| Tasks | 6 |
| Circuit topologies | 2 |
| Distinct requirement sets | 5 |
| Distinct reference parameter vectors | 2 |
| Failed requirements at each starting design | Exactly 1 |
| Tasks solved by replaying the corresponding public circuit default | 6/6 |
| Calibrated difficulty labels | None |

The AutoCkt references all use `CCOMP=20 pF`, `IBIAS=30 uA`, and `W_GM=80 um`. The Fan SMC references all use `CAPACITOR_0=5 pF`, `CURRENT_0_BIAS=60 uA`, and `MOSFET_23_1_M_gm3_NMOS=16`. Each is already visible in its circuit's public `reference.params`. AutoCkt starting failures are power, power, and DC error; Fan SMC starting failures are unity-gain frequency. The six tasks are useful pipeline fixtures, but repeating this construction 250 times would produce a weak benchmark even with unique task IDs.

## Evaluator findings and correction

### Corrected: individual constraint ambiguity could be accepted

`analog_design/simulator.py` previously compared only the two measurement paths' overall `success` values. When both paths failed a different constraint, a conflicting individual decision was accepted as `status: ok`.

Concrete counterexample: Python phase margin `59.99` degrees, native phase margin `60.01` degrees, minimum `60` degrees, with power above its limit in both paths. The phase difference is within the declared `0.05` degree crosscheck tolerance; both overall scores fail because of power, but the phase checks differ. The old evaluator emitted an apparently valid score despite this ambiguity.

The evaluator now compares the complete `checks` dictionaries. A discrepancy yields a failed evaluation and reward `-1`, using the existing error message. The existing scoring formula and valid-action rules are unchanged. A regression in `tests/test_evaluator.py` covers both directions of the conflicting phase decision while power fails in both paths. All 88 project tests passed after this change. The first sandboxed run was unable to bind the HTTP worker's loopback test socket; the authorized run outside the sandbox passed all tests.

This correction changes evaluator hashes: freeze the new hashes before generating and accepting benchmark evidence. Historical pilot records describe the older evaluator and must retain their original provenance.

### Remaining findings that matter when scaling

| Finding | Implication and action |
|---|---|
| Native and Python measurements use the same ngspice waveforms and PDK. | Describe this as two measurement implementations, not two independent physical simulations. Keep analytical fixtures and source-deck comparison evidence. |
| Passing references are checked once at the task's sample density. | Repeat accepted references with denser AC sampling and smaller transient steps, preserving original requirements and requiring the same per-constraint decisions. Reject boundary-only successes; record numerical margins. |
| `settling_tolerance_v` is part of the transient test, independent of `max_tracking_error_v`. | Tightening the tracking target does not change the settling band. Task descriptions must state both. The existing Fan SMC settling band is 20 mV for a 200 mV step (10%); it is not a 1% settling measurement. |
| Non-settling, missing unity crossings, ambiguous crossings, and invalid operating points become failed evaluations. | This is conservative and appropriate for admission. Track these separately from valid-but-unsuccessful designs; do not describe them as proven physical infeasibility or silently drop their budget cost during baselines. |
| `power_w` is DC quiescent supply power from the AC operating point. | Do not call it transient, average switching, worst-case, or total-system power. No transient-power constraint is implemented. |
| `gain_db` is gain at the finite AC starting frequency. | State the frequency. Do not conflate dB and V/V, and do not apply the existing normalized dB reward as if it were a physical gain ratio. |
| The amplifier interface and loop-breaking arrangement are fixed. | New amplifiers need pin-order, polarity, loading, and common-mode checks. Filters, comparators, oscillators, differential-output amplifiers, and other circuit classes need different testbenches. Merely adding a PDF is insufficient. |
| MOS dimensions depend on the supplied PDK's `.option scale=1.0u`. | Existing `W_GM` values are in micrometers; capacitance and current are in SI farads and amperes. Multiplicity is an integer count. Copying these numeric conventions into another model deck without auditing its scale would be wrong. |
| Action bounds are project rules, not a proof of the PDK's operating envelope. | Check new topology dimensions against the model's supported bins and inspect bias voltages, retained model warnings, and selected operating conditions. Do not label an arbitrary bounds expansion as physically qualified. |
| Per-run provenance hashes the corner entry file but not every recursively included PDK file. | Preserve the pinned archive and hash the extracted PDK tree or resolved include closure once per frozen environment. Recheck that hash before batch acceptance. Hashing `tt.spice` alone misses altered included models. |
| `evaluate` trusts the task JSON; it validates numeric actions, not arbitrary task paths, conditions, or netlist strings. | Only serve trusted, hash-bound task definitions through the catalog. Do not offer unrestricted user-written task JSON to a remote simulator service. New benchmark tooling should validate full trusted task schemas. |
| Version mismatch currently emits only a warning. | Benchmark release acceptance should require the frozen supported ngspice version or explicitly document and verify a compatible alternative. |
| The current unit/verification suite covers only existing circuits. | Add deliberate failure, nominal pass, unit, and numerical-refinement checks for every new topology before scaling it. Passing old tests does not validate new connectivity. |

No numeric-action code execution path was found in the inspected generation/episode route: model proposals cannot replace trusted topology, model, path, testbench, or conditions, and numeric actions reject booleans, nonfinite values, unknown parameters, out-of-range values, and nonintegral multiplicities. Invalid actions consume an episode slot. This is an API property, not operating-system isolation.

## Recommended admission protocol

1. **Qualify a circuit, then create task variants.** For each selected paper or released implementation, record title/version, figure or circuit name, source URL, pinned repository revision, local asset hashes, license, port order, process/models, and operating conditions. Summarize which circuit relationships the paper supports. Distinguish reproduced source facts, manually reconstructed details, process substitutions, and project-selected target values. A source quote matching text is not evidence of correct interpretation.
2. **Freeze each supported design domain.** State every editable parameter's unit and grid, fixed component assumptions, allowed bounds, model family, supply, temperature, load, common mode, stimulus, AC sweep, observation windows, and metric definitions. Use justified dimension ranges; avoid scaling difficulty solely by narrowing a hidden feasible region. Different loads or temperatures add operating conditions, not additional topologies.
3. **Characterize before selecting targets.** Sample the allowed domain using a documented seeded design. Include public defaults, bound checks, interior points, and nearby perturbations. Keep unsuccessful and invalid evaluations. Build a population of feasible designs across actual tradeoffs, rather than copying one seed and adjusting arbitrary decimal thresholds. Record a physical metric table for each topology/condition.
4. **Construct candidates with meaningful requirements.** Select feasible targets from the observed tradeoff envelope, rounded to engineering precision. Prefer distinct active constraints or combinations: speed/power, gain/stability, accuracy/settling. Keep broad quality floors. All requirements must be stated in the learner specification and evaluated. Do not infer omitted paper requirements or claim fabricated paper performance numbers.
5. **Require a useful starting point and a robust reference.** The start must return `status: ok`, fail at least one requirement by more than measurement ambiguity, and obey all action rules. The private reference must pass all requirements on both extraction paths, with recorded numerical margin. Re-evaluate both after writing the final task file. Reference refinement must preserve passing decisions. For a hard candidate, inspect nearby feasible witnesses or stable repeated/refined behavior so difficulty does not come from numerical fragility.
6. **Reject duplicates beyond IDs.** Check identical requirements, identical starts, shared reference vectors, near-identical normalized parameter locations, target-profile similarity, and empirical solution overlap. Every accepted entry needs an exclusion decision against the six pilot tasks and the earlier local accepted task. Use human-readable profiles and a similarity report; hashes alone only detect exact copies.
7. **Calibrate difficulty under frozen budgets.** Run the baseline panel below with recorded seeds and complete attempt traces. Choose the final 250 from a larger characterized candidate pool, preserving honest labels when candidate quotas are not met. The baseline results and admission criteria belong in the release.
8. **Freeze leakage groups and splits before learner training.** Use topology groups for topology transfer, and stronger clustered groups for familiar-topology interpolation. Audit solution replay across splits. Freeze task, evaluator, dependency, source, split, and baseline hashes; do not tune final-test task selection after evaluating the learner.
9. **Package public inputs and evaluator answers separately.** Export the actual learner-facing whitelist, hash it, and inspect it for answer leakage. Put private reference parameters, simulation evidence, generation requests, adaptive baseline trajectories, and calibration caches outside the learner's accessible filesystem. Keep training qualification pending until its actual review requirements are fulfilled; do not create fictitious reviewer records.

## Difficulty: a measured curriculum rather than a promise

The requested target allocation can be **100 easy, 125 medium, 25 hard**. These counts are a curation goal, not grounds to assign labels. Keep `proposed_difficulty`, `calibration_status`, and `measured_difficulty` distinct. If only 12 tasks meet a predeclared hard criterion, report 12 calibrated hard tasks and identify the remaining intended-hard candidates honestly.

Use the same 30-evaluation cap for every method and task; evaluate the initial design as the first charged attempt for all calibration baselines. Report this convention because the existing episode API also permits a learner to propose a change first. Changing the budget to manufacture hardness is a different benchmark. Record success at 5, 10, and 30 calls and calls to first success, counting unsuccessful runs as censored at the limit rather than omitting them.

Minimum baseline panel:

- **Public default replay:** after the initial evaluation, try the matching released/project default parameter vector, when within task bounds. This solves all six pilot tasks. A medium/hard task should not pass this trivial baseline.
- **Uniform random search:** preserve the existing linear-range baseline, with integer values sampled discretely. It detects large feasible volumes and establishes compatibility with historical results.
- **Log-scaled random search:** sample positive capacitance and current over log coordinates, with appropriate linear or integer coordinates for other parameters. Clearly disclose the sampling distribution; difficulty depends on it.
- **Adaptive local search:** use a simple, fully specified coordinate or trust-region optimizer in normalized coordinates, including integer handling, bounded restarts, and invalid-result behavior. It must consume the same observation API and logical budget without access to references or characterization tables.
- **Training-solution replay audit:** fit a small prototype bank using training tasks only, then test its known solutions against validation/test tasks. This measures memorization shortcuts that exact requirement hashing misses. It must not use held-out answers to build the bank.
- **Untrained target LLM:** needed before claiming that a cohort is hard for the intended learner, or that RL improves it. Freeze model revision, prompt, numeric formatting, sampling settings, token limits, invalid-action handling, and evaluation cap. If this run is deferred, label difficulty as baseline-relative only.

Implemented for this build: [benchmark/baselines.py](../benchmark/baselines.py) supplies `run_search(task, evaluate_action, method, seed, budget=30)` with `uniform_linear`, `uniform_log`, and `coordinate_search`. The latter starts with a normalized step of `0.25`, probes both directions for each coordinate in seeded order, halves its step after an unsuccessful sweep, and restarts after two stalled sweeps. Capacitance/current/geometry coordinates use their documented log transform; integer multiplicities use discrete rounding. All methods count the initial evaluation, skip duplicate proposals with bounded retry work, cap to the task's own budget, stop on success, and emit complete public trajectories. Infrastructure exceptions propagate. Eight focused tests pass, including deterministic mixed-domain actions, exact budgets, failures, finite-domain exhaustion, and adaptation on a known log-coordinate objective. This implementation is ready for circuit calibration; these synthetic tests do not establish circuit task difficulty. Default replay, training-solution replay, and an untrained LLM remain separate calibration/audit calls.

The implemented rule in `benchmark/select.py` is: easy if at least one declared baseline solves at least 80% of seeded runs and has a median of at most ten charged calls, with failures censored at thirty; hard-candidate if default replay fails and every declared search baseline solves no more than 20% of runs within thirty calls; medium for the remainder. Every method needs at least ten completed seeds for easy or medium, and twenty for confirmed hard. Publish all per-method outcomes rather than only the strongest aggregate, including confidence intervals; `0/3` or `0/5` is weak evidence. Baseline failure does not prove hardness against every optimizer. An adaptive baseline with high success but slow convergence deserves a separate description instead of an inflated hard label.

If runtime permits only a small calibration panel, report **provisional baseline-relative cohorts** and exact empirical success counts. Selecting the hardest 25 by quantile is acceptable if labeled “hardest within this collection”; it does not establish absolute hardness. Never use only constraint count, number of transistors, distance from the reference, target tightness, or a paper's reputation as a difficulty label.

### Efficient but fair calibration

Physical simulation can be reused when topology, PDK, parameters, operating condition, testbench, numerical settings, and evaluator hashes match exactly. Metrics are independent of task thresholds; a shared pool of nonadaptive random candidates can therefore be simulated once and scored against several tasks. The cache key must cover the full simulation identity and store raw measurement agreement evidence, not merely a final reward.

Each replayed logical attempt still spends a task's evaluation slot. Report logical evaluation count and actual simulator invocation count separately. Adaptive local search must select its next point using only the current task's prior observations; a global characterization table must not become an oracle. Independently seeded baseline trajectories can share physical cache entries, but do not treat outcomes across correlated tasks as independent when estimating uncertainty. Invalid physical simulations remain invalid for every threshold set, and per-constraint agreement must be checked anew for each task because a tighter threshold can expose previously harmless interpolation differences.

## Splits and effective diversity

A provisional size target is **175 train, 25 validation, 50 test**, but group integrity takes precedence over exact split ratios. These are 250 total tasks, not 250 training tasks plus a separate evaluation corpus. If the user's final intent requires 250 for training alone, create an additional held-out corpus before measuring generalization.

The current generator's `requirement_group` is an exact identity over topology, conditions, parameter rules, testbench, requirements, and budget; different starts share a group. The training catalog's `requirements` grouping is coarser and omits parameter rules and budget, while still splitting nearby but numerically unequal thresholds. Neither prevents near-duplicate leakage or shared passing solutions.

For a familiar-topology benchmark, assign whole groups defined by circuit family, operating condition, target-profile cluster, reference/design neighborhood, and generation family. Declare the clustering rule before splitting. Measure cross-split target/parameter distances and replay training solutions against held-out tasks. Avoid presenting overlapping easy variants as evidence of extrapolation.

For a structural-generalization benchmark, hold out entire topology families, including small netlist variants derived from the same parent architecture. The two existing topologies cannot provide independent topology-held-out train, validation, and test splits. More verified topologies are needed. If the final corpus still has only two or a few amplifier architectures, describe its scope as circuit-sizing tasks on those architectures, not a general analog-design benchmark. Report counts per topology, parent paper, operating condition, target profile, distinct reference, distinct feasible basin, and active-constraint pattern. Task count alone overstates effective sample size when several tasks share a broad solution region.

## Answer leakage and learner packaging

`Episode.specification()` currently exposes `id`, `conditions`, `parameters`, `constraints`, `ac`, `transient`, current numeric parameters, and remaining budget. It omits circuit directory, netlist path, reference vector, private rationale, and generation evidence. Parameter names such as `W_GM` convey physical meaning and do not themselves disclose a correct value. Generated IDs are based on public task identity and starts, not the private reference, so they do not directly encode an answer. They can still be used as a lookup key if answer-bearing artifacts are accessible.

There are real answer-bearing public artifacts: both `circuits/*/reference.params`, AutoCkt's `source.json` reference section, nominal tasks, generation examples, old generation requests, and the second action of every tracked pilot `episode.json`. The repository therefore cannot be treated as an answer-free learner filesystem. Private directory names alone provide no isolation. Also, many pilot initial parameters already equal the reference on two of three dimensions; this is valid for easy exercises but insufficient variation for an entire curriculum.

For the new corpus, export an explicit learner package containing only task specifications, allowed action/schema documentation, metric definitions, source attribution, and optional circuit connectivity/parameter-role descriptions with editable values represented symbolically. Fixed component values may be included when they are genuinely fixed. Keep new solution parameters, candidate pools, provenance requests containing seed references, baseline successful trajectories, and measured reference metrics in a separate evaluator package. A model trained only through the worker needs no filesystem or shell access. Run that learner under an account/container that cannot read the evaluator archive, and retain an access-manifest audit. The existing authenticated loopback API strips private paths from public responses but does not provide OS isolation for a trusted trainer that can read the full repository.

The current specification contains no circuit graph or circuit explanation beyond parameter names and task ID. If the intended experiment measures paper-informed analog reasoning, include a sanitized topology diagram/netlist and parameter roles in the learner observation, with equal access for baselines that can use such information. Otherwise describe the task accurately as low-dimensional circuit sizing from numeric specifications and simulator feedback.

Implemented for the new benchmark: [benchmark/learner.py](../benchmark/learner.py) exports explicit public specifications, verifies task content hashes before export, and writes only specification files, a small public index, and metric/action documentation. `public_specification(task)` includes sanitized paper attribution, symbolic circuit connectivity, parameter roles and fixed values, and the starting design. It rejects structured answer/default/trajectory fields and editable values embedded as fixed parameters or netlist assignments. `BenchmarkEpisode` inherits the existing constructor and approval gate, adding this safe context to observations while retaining live parameter values and remaining budget. `export_learner_bundle(index_path, output_directory)` never opens reference paths or copies evaluator directories. Seven focused packaging/episode tests pass, and all ten prepared domain contexts pass the sanitizer. This is artifact separation, not operating-system isolation or a guarantee that arbitrary prose cannot disclose an answer; final task narratives still need review.

## Release contents and permitted claims

The release should include an index of exactly the accepted tasks, learner package, private references, per-task starts/reference results, refinement results, rejected-candidate reasons, all provenance hashes, calibrated or explicitly provisional difficulty labels, baseline results and seeds, split manifest, paper adaptation notes, reproducible commands, and a dataset card with the concrete supported circuit classes and measurements. Store full private evaluator assets locally even if public exports exclude them. Do not expose reference metrics in a learner-facing index as an extra optimization oracle.

Appropriate claim after passing the automated protocol: “250 feasible simulator-verified sizing tasks across N documented circuit topologies under the listed conditions, with baseline-relative difficulty measurements.” Stronger claims require additional evidence: paper-result reproduction needs matching source conditions and model verification; PVT robustness needs the declared corner/voltage/temperature combinations; learned improvement needs matched held-out comparisons and repeated training seeds; silicon performance needs physical implementation and measurement. Creating a dataset cannot guarantee the “best model.”

Immediate implementation priorities: retain the corrected per-constraint check; include default replay in calibration; freeze complete simulation/cache identities; independently re-evaluate final task files and refined references; keep private solution artifacts outside learner exports; and make all remaining unperformed checks explicit in the release status.

## Independent release verifier delivered

[benchmark/verify_release.py](../benchmark/verify_release.py) and [scripts/verify_benchmark.py](../scripts/verify_benchmark.py) provide an independent final bundle check. The verifier validates task/reference hashes and paths, complete finite parameter vectors and integer rules, all eight metric directions, 30-call budgets, source files against pinned hashes, topology/condition identity against the trusted domain catalog, unique references within each topology, and both declared and independently recomputed requirement groups across splits. Public context cannot list editable values as fixed parameters. Existing approval claims must be supported by the real qualification mechanism; no approvals are created.

Run `python3 scripts/verify_benchmark.py --index datasets/analog_benchmark_250_v1/index.json --expected-count 250 --simulate --workers 4 --output runs/benchmark_release_verification_001` after the final bundle exists. The output directory must be new. Without `--simulate`, the report explicitly has `scope: static_only` and `publication_ready: false`. With it, each final task receives fresh initial, reference, and refined-reference evaluations through the core evaluator, preserving every result and raw simulator artifact. The refined reference doubles AC points per decade and halves the transient step while preserving the original constraints. Scores and every native/Python decision are recomputed from the returned measurements; generator success fields and simulation caches are unused. Recorded refinement deltas characterize two resolutions and do not prove continuous numerical convergence or physical robustness. Difficulty labels are checked as metadata; baseline calibration remains a separate audit.

The verifier also runs one fresh public-default measurement per topology and independently rescores both measurement paths for each final task. A task that the default solves is rejected. An invalid or ambiguous default is recorded as unresolved, with its exact artifacts and affected task IDs, and prevents publication; it does not become evidence of physical infeasibility or hardness. Reference-distance admission uses a minimum normalized log RMS separation of `0.025` within each topology, configurable with `--minimum-reference-distance`. Every nearest-neighbor and pairwise distance is reported. The fresh private reference measurements are rescored across all tasks of the same topology and conditions, producing per-reference coverage, ambiguous/unresolved cases, and a deterministic greedy set-cover count. These counts expose shared solution regions; they are neither optimal set-cover certificates nor general hardness measurements.

Fourteen targeted verifier tests passed. A real one-task AutoCkt regression verifies the public-default gate: its start, reference, and refined reference have their expected outcomes, but the task is correctly rejected because the fresh public default also solves it. Evidence is at `runs/benchmark_verifier_default_replay_smoke_001/verification.json`. This validates the rejection path on a known exercise; it is not verification of the future 250-task release.

## Calibration-to-release integrity audit

The first assembly implementation trusted summary statistics and admission JSON without checking their checkpoint envelopes. A controlled temporary fixture demonstrated the consequence: assembly accepted an index of 250 hard labels despite zero baseline trial files, an empty calibration manifest, and admission checkpoints marked incomplete with invalid payload hashes. The fresh circuit verifier deliberately does not validate difficulty, so this needed a separate correction before assembling the release.

[benchmark/release.py](../benchmark/release.py) now requires 250 distinct selected IDs and exactly 100 easy, 125 medium, and 25 hard tasks before creating an output directory. It validates safe candidate/index paths, the frozen calibration configuration, required code/domain/candidate hashes, complete SPICE include dependencies, source identity, physical cache/result hashes, and admission/trial checkpoint identities and payloads. Admission decisions are recomputed from measurements. Each trial is replayed through its declared deterministic baseline using recorded observations, checking every generated action, logical budget charge, measured reward, and stop condition. Its observations must agree with the corresponding physical cache evidence. Per-method statistics are reconstructed from actual, distinct configured seed checkpoints and compared with the summary. Hard requires at least twenty completed trials of every declared method; ten unsuccessful trials remain a hard candidate. Final output copies only explicitly validated checkpoint files into the private package and checks input hashes again before writing its index. The release still awaits the separate fresh-simulation verifier.

Thirteen new integrity regressions passed, and the broader benchmark suite passed all 92 tests. One real completed screening task also passed checkpoint and physical-cache auditing; with one seed per method its calibrated difficulty correctly remained incomplete. Calibration code, candidate/domain data, and the core evaluator were not modified during this audit. The selection module remains a provisional summary-driven screening tool; final assembly independently validates its evidence and labels. Existing calibration summaries must stop changing before a final assembly, because their hashes are included in the assembly snapshot.

## Fixed frontier targets and starting-design variants

The initial frontier constructor selected one start per reference using an index-based easy/medium/hard hint. When controlled starts were supplied it discarded the global measured pool, making distant starts unavailable. It also selected targets again from the current discovery pool, which could change requirements after controlled starts had been measured against an earlier saved target file. Those construction choices reduce useful calibration coverage without supplying any evidence of difficulty.

[benchmark/frontier_candidates.py](../benchmark/frontier_candidates.py) now accepts `--targets-file` and `--maximum-targets-per-topology`. Saved definitions and order are retained exactly. Their reference rounding, characterization key, constraint derivation, requirement group, discovery-support metadata, and original source/settings/parameter-deck evidence are verified. Historical discovery directories may differ from published circuit directories, and formerly fixed components may have become editable; equivalence is checked using source hashes and the archived numeric parameter deck. Fresh admission still evaluates the current, fully rounded task and reference using the current full-domain identity. All 774 prepared target definitions passed these archive checks; limiting to the first fifty per topology retained exactly 500. This is target-construction validation, not a claim that 500 tasks have completed admission or calibration.

The constructor emits up to three distinct starts per target: `nearest` prefers target-tagged controlled changes, `intermediate` prefers a controlled start with at least two substantive actual parameter changes and falls back to a global start with that change count and at least two clear failures, and `distant` uses a far global start. For the fallback, normalized distance near 0.2 is preferred. `--variants` can select a subset for diagnostic experiments. Actual perturbation kind, requested and realized factors, changed controls, and measured distances are retained. The constructor recomputes substantive changes from the rounded vectors: integer difference at least one, or continuous normalized log difference at least 0.025. It does not trust nominal two-control tags when clipping left only one real change. Duplicate rounded starts are omitted instead of being counted twice. Construction fields remain hints, and every variant requires independent calibration. Twenty-nine focused frontier tests pass, covering these contracts and archived source/parameter identity.

Every variant shares its target's reference and requirement group. Both selection and final assembly already reject repeated references and repeated groups, so a pool of up to 1,500 candidates from 500 targets cannot become 1,500 claimed independent tasks. Select only one variant from each group, then independently check reference coverage on the final subset. A low maximum single-design coverage in the entire prepared pool does not guarantee the same fraction in a selected subset. The archived per-target feasible-set signatures describe their original measured discovery pool; current-pool coverage is recomputed and reported separately, not silently substituted for those saved statistics.

Operational constraints: use a new candidate directory and freeze its index before calibration. A small separate canary pool is diagnostic; its checkpoint configuration hashes bind that exact index and candidate paths, so its trials cannot be copied into a later larger pool. The current release assembler takes one candidate directory; combining independently frozen pools requires a new confirmation run or an explicit multi-pool provenance extension. A separate v2 measurement-cache directory is supported when its physical/configuration/result hashes match the calibration manifest. No cache entry may be relabeled to match a new task or domain identity. When supplying multiple calibration summaries to the provisional selector, later entries for the same task currently replace earlier entries; put the intended complete confirmation run last, and rely on final assembly's checkpoint audit rather than that order as evidence.

## Engineering shortcut audit and fourth baseline

The controlled starts expose an important calibration weakness: a factor-two change in one control can be repaired by an anchored half/double sweep, even if an optimizer's normalized step misses that physical factor. A task should not receive a hard label solely because the original three methods lack this simple move. [benchmark/engineering_search.py](../benchmark/engineering_search.py) therefore supplies `run_engineering_sweep(task, evaluate_action, seed, budget=30)` without reading references or construction metadata. It charges the initial design, visits controls and half/double directions in seeded order, and keeps every initial probe anchored to the original start. With sufficient budget, a solution equal to one such canonicalized probe is tested within at most `2*N + 1` charged evaluations. This statement covers that explicit shortcut, not arbitrary proximity to a solution or recovery after bound clipping.

After the anchored sweep, the baseline combines independently reward-improving single-control moves, then uses incumbent-centered factors 1.5 and 2/3, shrinking the log step after a stalled sweep and making bounded random restarts after two stalls. Positive controls are treated generically, including integer multiplicities and resistance; nonpositive domains use a documented additive fallback. Bounds, integer rounding, fifteen-significant-digit serialization, duplicate skipping, failed-query charges, and early success follow the existing baseline contract. Feedback-guided combinations are heuristic and need not solve interacting two-control problems.

Fourteen focused engineering-baseline tests pass. The proposed four-method dispatcher also passed the ten existing baseline-contract tests when staged entirely in memory. [reports/engineering_sweep_integration.patch](engineering_sweep_integration.patch) adds the fourth method/dispatcher and freezes the new module through calibration's `CODE_FILES`; its patch application check passes. At the time this patch was prepared it remained unapplied because active characterization runs guarded the existing baseline/calibration files. Apply only after those runs finish, then create new calibration manifests. The physical simulator/cache identity is unchanged by this baseline-only integration, so matching physical evidence may be reused while logical attempts and new trial/checkpoint identities remain distinct. Prior three-method labels alone cannot satisfy the resulting four-method difficulty contract.

## Existing numeric worker catalog compatibility

The evaluator release's `index.json` is not directly consumable by `training.catalog.load_catalog`: its task paths are relative to the bundle, its split policy is `topology_family`, and it lacks the loader's topology `group` field. [benchmark/worker_catalog.py](../benchmark/worker_catalog.py) supplies a narrow adapter. After the release's independent verification gates pass, run:

```sh
python3 -m benchmark.worker_catalog --index datasets/analog_benchmark_250_v1/index.json
```

This creates a new `worker_catalog.json` alongside the index, without rewriting tasks. It verifies task hashes/IDs and safe paths, independently requires every topology family to occupy one split, checks each topology's family assignment, and computes `group_key(task, "topology")`. The resulting task paths are project-relative, and `split_policy` is `topology`, as required by the unchanged loader. Exact original split assignments and a family-to-split map remain in the catalog. The adapter also rejects any overlap under the worker's coarser topology grouping. It validates the result with `load_catalog(path, training=False)`; seven focused compatibility tests pass.

This catalog belongs in the trusted evaluator bundle, not the learner-only specification export. Export reads only the index and task files; it never follows reference paths, reads solutions, invokes a server, or grants qualification. Its checks establish catalog/hash/split compatibility, not fresh simulator verification. Training mode continues to require the existing genuine per-task approval records.

The current `training.worker` imports and constructs `analog_design.episode.Episode`. Thus the exported catalog works with its existing numeric-action/numeric-observation flow, but paper and symbolic-netlist context from `BenchmarkEpisode` is not automatically exposed. Wiring that wrapper into the worker would be a separate integration change. The adapter explicitly records `benchmark_episode_context_active: false`; this work does not claim that a context-enabled worker or an RL training run has already been launched.
