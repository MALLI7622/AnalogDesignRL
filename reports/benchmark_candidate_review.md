# Candidate-generation review

Reviewed 2026-09-10 before candidate calibration. Files reviewed: `benchmark/candidates.py`, prepared `benchmark/domains.json`, and relevant rounding, scoring, baseline and release-verification code. This report is a review snapshot; subsequent fixes must be checked against the final release. No generator, domain or evaluator files were changed by this reviewer.

## Actionable findings

1. **High: the public-default rejection can silently disappear.** `create_candidates` finds the default measurement by exact dictionary equality, whereas exploration rounds continuous values to four significant digits. In the prepared catalog, eight of ten public defaults differ numerically from their rounded values. For example, AutoCkt's `IBIAS=2.9999999999999997e-05` becomes `3e-05`; the HoiLee bias behaves similarly. `default_rows` can therefore be empty and the `if default_metrics` rejection is bypassed. Canonicalize defaults consistently and reject candidate creation if the required default measurement is missing. Do not interpret missing data as a failing baseline.

2. **High: final verification does not independently enforce that same public-default requirement.** The reviewed `_simulate_record` evaluates the task-specific initial vector, the private reference, and the refined reference. It does not evaluate the upstream/project public default. A generated initial vector can fail while a readily available public seed passes. Measure each topology's public default freshly, then independently rescore that measurement against every final task; include the evidence in the release audit. Such reuse within a topology is valid only under identical physical conditions and measurement settings.

3. **Medium: imported discovery rows have no checked physical lineage.** `load_designs` accepts same-name rows, fills missing parameters from defaults, and checks only metric keys and parameter bounds. A discovery file generated under a different testbench, netlist or fixed parameter value can be accepted. The IAC extension illustrates why explicit lineage matters: adding Ra is safe for older rows only if their fixed resistor really was the exact current default. Check archived circuit/model/testbench identities, distinguish changes that only widen bounds from changes that affect physics, and remeasure unresolved rows. Reject nonfinite metric values and nonintegral integer controls explicitly instead of relying on later stages.

4. **Medium: rounded solutions and initial states need measured evidence.** Candidate construction scores stored measurements and then rounds output vectors to four significant digits. Older discovery files may contain unrounded vectors. Near thresholds, the resulting vector is a different circuit. Fresh final validation catches this, but calibration should also use the exact rounded public initial vector and private reference that will be released. Recompute the recorded initial failures after that measurement.

5. **Medium: distinct reference hashes do not establish useful solution diversity.** Current distance checks compare each reference against the default and its chosen start, not against other references. Selection balances exact reference usage, and the independent verifier rejects exact duplicate references, but arbitrarily close references remain possible. Measure pairwise normalized parameter distances among final references and build a reference-by-task feasibility matrix per topology. Report the largest number of tasks solved by a single reference and select against near clones or overwhelming single-vector coverage. Related rounded target vectors may still represent legitimate tradeoffs, but a new filename and a nearby solution are insufficient evidence of task diversity.

6. **Medium: pool feasibility is descriptive, not calibrated difficulty.** `empirical_pool_feasible_count / empirical_pool_valid_count` uses only valid simulator outcomes; it excludes failed designs and can include deliberately sampled neighborhoods near known good designs. It is not a probability of success under random search. Keep it labelled as discovery-pool coverage. Assign final difficulty from independently seeded, bounded baseline episodes after freezing the exact task contract; count failed simulations and initial evaluations in each episode's budget.

7. **Low: log-baseline scope should remain explicit.** The current baseline code samples continuous quantities logarithmically but integer multiplicities uniformly, including in `uniform_log`. This is documented in the implementation and is a defensible baseline choice, but half of many domains' controls are integers. Report that choice with difficulty results. Log-coordinate integer proposals or a separate multiplicity-aware baseline would provide a useful additional comparison; failure of the present baselines alone does not establish difficulty for an analog-design expert.

## Source and physics assessment

The prepared domains preserve the reviewed upstream load and common mode and state the SKY130/nominal/project-target scope. The three Leung variants have a shared family, which is correct for source-family splits. Parameter units are consistent with the released SPICE expressions: capacitors in farads, reference currents in amperes, multiplicities as integers, AutoCkt widths in micrometers, and IAC resistance in ohms. Source device expressions already contain mirror factors; the prepared domain does not multiply those factors a second time.

The broader IAC Cm range and added Ra control are physically justified by the original paper's pole-separation analysis, as documented in `reports/benchmark_paper_sources.md`. Large compensation capacitances in other domains may exceed the released load at the upper bound; this is not intrinsically invalid for a sizing search. It does mean the search includes deliberately slow or area-expensive designs. No capacitor-area objective is currently verified, so labels such as “minimum area” or “area efficient” must not be inferred from those solutions.

AnalogGym domains use a 20 mV settling band for a 200 mV step (10%); AutoCkt uses 2 mV for a 100 mV step (2%). These are explicitly recorded and should remain visible in task descriptions and dataset documentation. A tight final plateau-error requirement does not turn the recorded 10% settling time into 1% settling time. The eight fixed metrics cover gain, unity crossing, phase margin, nominal supply power, DC error, plateau tracking error and rise/fall settling under one prescribed experiment. They do not establish noise, mismatch, layout, distortion, output-current or PVT performance.

Song's original full-text/figure review remains limited. The domain preserves that limitation in its source metadata; retain it in final provenance and avoid claiming that every original paper was fully read. The correction of the swapped ACBC/IAC references is reflected in the domain source records.

## Generation method and difficulty claims

Source-grounded deterministic simulation-guided curation is appropriate here. There is no quality requirement to make one language-model call per task. The relevant evidence is that the circuit structure is understood, requirements are engineering-rounded and nontrivial, a solution is demonstrably feasible, and the solver sees only its allowed observations. The code honestly distinguishes proposed difficulty from calibrated difficulty and records the generation mode.

Target rounding is conservative: minimum targets round down, maximum targets round up, with template quality floors retained. Reference slack is checked before acceptance, and the 60° phase-margin floor is preserved. Final labels must still come from empirical results rather than `proposed_difficulty`, number of failed initial checks, geometric distance to a known solution, or a narrow margin alone. Calibration used to choose tasks should be separated from any reported post-selection baseline result; fresh audit seeds and uncertainty/counts avoid presenting selection-biased estimates as held-out performance.
